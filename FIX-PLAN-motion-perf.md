## § 1 · FULL SCOPE DEFINITION

### 1.1 What this plan accomplishes

Four outcomes, all inside the existing WebView app:

1. **Android Back closes the top open overlay** instead of sending the app to the launcher. CP-01 proved 8 sheet/modal overlays share one `showModal`/`hideModal` pair, plus the big screen. One shared helper serves all of them.
2. **A heartbeat glow on the emergency line.** ⚠ **BLOCKED — see §1.6.** CP-01 found two elements that "emergency line" can mean. The animation technique is settled and identical for both; only the selector is open.
3. **Lower render cost** on three measured-expensive animations: `box-shadow` on an infinite loop, `filter` blur in card entry, and `backdrop-filter` on every dialog open.
4. **A measured before/after**, so "faster" is a number and not an impression.

**What must NOT change:** tab switching stays a plain render (`state.tab=t;render();window.scrollTo(0,0)`); no View Transitions API; the app keeps exactly two `setInterval` timers; no new dependency; no change to what any screen renders or to any data path; visual design unchanged apart from the new glow.

#### Proof — data flow summary

- **Rendering.** `render()` (`src/shell.js:33`) rebuilds `#main` wholesale on every state change: header chip, nav, then `renderMain()` or `renderServeView()`, then `persist()`. Tab switching is a plain re-render; motion comes from CSS entry animations on the newly inserted cards (`.stagger`, `.pour`), not from any JS animation loop.
- **Overlays.** Eight sheets/modals are opened by `showModal(sel)` and closed by `hideModal(sel)` (`src/volunteer.js:887–888`). `hideModal` adds `is-closing`, waits 260 ms, then adds `hidden`. The big screen (`#tv`) bypasses this pair and toggles `hidden` itself in `src/queue.js`. Five overlays close with nothing but `hideModal`; three (`#notifSheet`, `#queueModal`, `#placeSheet`) also reset state, so Back must call *their* close function, not `hideModal` directly.
- **Back key.** `MainActivity` does not override `onBackPressed`, so Android Back drives WebView history. A single-page app has no history entries, so Back exits the app. The fix is to give each open overlay one `pushState` entry.
- **Weak devices.** `src/shell.js:168` adds `html.lite` when `hardwareConcurrency <= 4` or `deviceMemory <= 2`, then measures frames for ~1.5 s and downgrades if choppy. But `.lite` only has six rules and does not disable `qpulse`, `scrim`'s `backdrop-filter`, or the `filter` blur in `rise`/`pour` — the exact animations the audit flags as paint-bound.
- **Build.** `src/` → esbuild → inlined into `dist/index.html`. The harness runs the same bundle in a Node `vm` with a stub DOM, so anything the app touches at module load (such as `window.history`) must exist in that sandbox.

**CHANGE 1 — shared overlay history helper**

BEFORE:

```js
/* One browser-history entry per open overlay, so the Android Back key closes the top overlay
   instead of leaving the app. A single-page WebView has no history of its own, so without an
   entry Back goes straight to the launcher (measured on ctv390, 2026-10-29).

   Keyed by selector, not by call order: an overlay that is already open must not push a second
   entry, and an overlay closed out of order must remove its own entry rather than the newest. */
const open = [];
let ignoreNextPop = false;

/** Register an overlay that has just become visible. `close` is that overlay's own close function. */
export function overlayOpened(key, close) {
  if (open.some(o => o.key === key)) return;
  open.push({ key, close });
  history.pushState({ overlay: key }, '');
}

/** Deregister an overlay closed from the screen (X, Escape, backdrop) rather than by Back. */
export function overlayClosed(key) {
  const i = open.findIndex(o => o.key === key);
  if (i < 0) return;
  open.splice(i, 1);
  ignoreNextPop = true;
  history.back();
}

/* Back: close the top overlay. Its close function calls overlayClosed, which finds nothing left
   to remove for that key and so does not step history a second time. */
window.addEventListener('popstate', () => {
  if (ignoreNextPop) { ignoreNextPop = false; return; }
  const top = open.pop();
  if (top) top.close();
});
```

### § 1.7 · OPEN DECISION — how should Android Back reach the overlays?

CP-07 proved the Back work cannot function in the Android app without a change outside §1.2 scope
(evidence in A.5.3). The JS is correct and already works in the browser. Three ways forward:

| Option | Change | Cost | Note |
|---|---|---|---|
| **A** | Install `@capacitor/app` and register a `backButton` listener that closes the top overlay, else allows exit | New dependency (official Capacitor plugin; the app already has 3) + a small JS change | The documented Capacitor way. Gives JS full control. |
| **B** | Override `onBackPressed` in `capacitor/android/.../MainActivity.java` to call `webView.goBack()` when `canGoBack()` | ~6 lines of Java, no new dependency | Works with the pushState code already written. Touches `capacitor/**`, currently §1.3 OUT of scope. |
| **C** | Ship the JS as-is | None | Back works in the browser/PWA. The Android app keeps the bug. |

**RESOLVED 2026-10-29 — the operator chose Option A.** Scope widened accordingly (A.6.5). Implemented as
CHANGE 11 and verified on the device: Back now closes the top overlay and the app stays in the
foreground, while Back with nothing open still exits.

> **Why a JS listener was required, not just the plugin.** Reading
> `@capacitor/app/android/.../AppPlugin.java:46–60`: with no JS listener the plugin calls
> `webView.goBack()` when `canGoBack()`, which alone would have fixed the overlay case. But the
> `OnBackPressedCallback` is *enabled*, and when `canGoBack()` is false the branch does nothing —
> so Back would have been swallowed and the app could not be exited. Registering a listener moves the
> decision to JS and avoids trading one bug for another.
